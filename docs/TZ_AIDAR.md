## 0. Контекст (прочитай перед началом)

Ты работаешь в проекте **«Автономный AI-маркетолог»** — Telegram-бот для хакатона «Кибер 102»
(АО «Салаватстекло»). Репозиторий: `https://github.com/Yralskui/ai-marketer`, Python 3.11+,
aiogram 3, SQLAlchemy 2 async, весь код асинхронный.

Сделано всё, кроме «мозгов»: компании, согласование постов, публикация в канал, расходы,
комментарии, отчёты, фотобанк, деплой на сервер. Бот уже работает на сервере, но в **mock-режиме**:
тексты и картинки — шаблонные заглушки. **Твоя задача — подключить настоящую нейросеть GigaChat**
и сделать AI-функции.

Обязательно прочитай в репозитории:
1. `CLAUDE.md` — правила проекта: где что лежит, что нельзя менять, стиль кода.
2. `docs/AI_OPTIONS.md` — почему GigaChat, цены, что с ChatGPT.
3. `docs/ARCHITECTURE.md` — как устроены агент и провайдеры.
4. `app/llm/base.py`, `app/llm/openai_provider.py`, `app/llm/mock_provider.py` — интерфейс
   LLM и примеры провайдеров.
5. `app/agent/core.py` — цикл агента (как он вызывает модель и инструменты).
6. `app/images/base.py`, `app/images/mock_provider.py` — интерфейс генератора картинок.

Почему GigaChat: сервер стоит в России, OpenAI оттуда отвечает 403. GigaChat доступен,
у физлица есть **бесплатный пакет на 12 месяцев** (250 млн токенов Lite, 40 млн Pro, 25 млн Max),
он умеет вызывать функции и рисовать картинки (встроенная функция `text2image`).

## 1. Подготовка (один раз)

1. Склонируй репозиторий и поставь окружение — раздел «Быстрый старт» в `README.md`.
   Проверь, что всё зелёное:
   ```bash
   ruff check . && ruff format --check . && pytest && python -m app.main --check
   ```
2. **Создай свой тестовый бот** через @BotFather и впиши его токен в свой `.env`.
   ⚠️ Боевой токен `@ai_marketolog1_bot` локально **не запускай**: он уже работает на сервере,
   два процесса с одним токеном мешают друг другу.
3. В свой `.env`: `ALLOWED_USER_IDS=<твой Telegram ID>`, `TELEGRAM_CHANNEL_ID=` — свой тестовый
   канал, куда твой бот добавлен админом. `PUBLISH_DRY_RUN=true`, пока отлаживаешь.
4. Получи ключ GigaChat: developers.sber.ru → GigaChat API → создать проект для **физлица** →
   «Ключ авторизации» (Authorization key), scope `GIGACHAT_API_PERS`. Ключ — **только в `.env`**,
   в Git не коммитить.
5. Работай в ветках: `git pull --rebase origin main`, потом `git switch -c feature/gigachat-llm`.
   Одна задача — одна ветка — один PR. Коммиты по Conventional Commits на английском
   (`feat: ...`), комментарии и тексты — на русском.

## 2. Задачи по порядку

### Задача A1 — провайдер GigaChat для текста (P0, главная)

**Цель:** с `LLM_PROVIDER=gigachat` бот пишет нормальные посты, а агент сам вызывает инструменты
(создать черновик, показать посты, правка, отчёт).

**Файлы:**
- новый `app/llm/gigachat_provider.py` — класс `GigaChatProvider(LLMProvider)`, `name = "gigachat"`;
- `app/llm/factory.py` — ветка `if provider == "gigachat": ...`;
- `app/config.py` — новые настройки;
- `.env.example` — те же настройки с русскими комментариями;
- `requirements.txt` — зависимость, если берёшь SDK;
- новый `tests/test_gigachat_provider.py`.

**Настройки:**
- `GIGACHAT_CREDENTIALS` — ключ авторизации (base64-строка из кабинета);
- `GIGACHAT_SCOPE` — по умолчанию `GIGACHAT_API_PERS`;
- `GIGACHAT_MODEL` — по умолчанию `GigaChat-2-Pro` (варианты: `GigaChat-2`, `GigaChat-2-Max`);
- `GIGACHAT_VERIFY_SSL` — по умолчанию `true`. У API сертификат российского УЦ (Минцифры): либо
  поставь корневой сертификат, либо для разработки `false`.

**Как подключаться.** Можно взять официальный Python SDK `gigachat` (pip) — он сам получает и
обновляет OAuth-токен (живёт 30 минут). Можно и через `httpx` напрямую. **Сверь детали с
официальной документацией** developers.sber.ru/docs/ru/gigachat: адреса OAuth и API, формат
функций, лимиты.

**Главное — конвертация формата.** Агент передаёт провайдеру сообщения и инструменты в формате
OpenAI (см. `app/llm/base.py`):
- `messages`: роли `system`, `user`, `assistant` (может быть `tool_calls`), `tool` (`tool_call_id`,
  `content` — JSON-строка результата);
- `tools`: `[{"type": "function", "function": {"name", "description", "parameters"}}]`.

У GigaChat свой формат функций. Провайдер должен:
1. `tools` → `functions: [{"name", "description", "parameters"}]` и `function_call: "auto"`.
2. Сообщение `assistant` с `tool_calls` → `assistant` с `function_call: {"name", "arguments"}`.
   У GigaChat аргументы — объект, а не строка: распарсь JSON.
3. Сообщение `tool` → роль `function` с `name` инструмента. В сообщении `tool` имени нет, только
   `tool_call_id`: найди имя по `id` в предыдущем `assistant.tool_calls`.
4. Ответ модели с `function_call` → `LLMResponse(content=..., tool_calls=[ToolCall(id=<сгенерируй>,
   name=..., arguments=dict)])`. GigaChat зовёт функции по одной — это нормально, агент сделает
   следующий шаг.
5. `json_mode=True` (используется для профиля, ответов на комментарии, отчётов): если у GigaChat
   нет режима JSON, добавь в системный промпт требование «ответь только JSON-объектом». Наш код
   и так достаёт JSON из текста (`parse_json_object`).
6. Параметр `task` — только для логов.
7. **Ошибки:** сеть, 429, 5xx — повтор через `app/utils/retry.py::retry_async`. После всех
   повторов — `LLMError` с понятным текстом. Никаких «голых» исключений наружу.
8. **Расход токенов:** положи ответ в `LLMResponse.raw` так, чтобы `raw.usage.prompt_tokens` и
   `raw.usage.completion_tokens` читались **атрибутами**. Если у тебя dict — оберни в
   `types.SimpleNamespace`. Тогда `/costs` посчитает точно, иначе оценит по длине текста.

**Что ещё:**
- Прогони живьём сценарий: `/onboarding` с описанием компании → `/done` → «напиши пост про акцию
  с картинкой» → «✏️ Изменить» («короче и с эмодзи») → «что ты знаешь о нашем бизнесе?» →
  «покажи мои посты». Агент должен выбирать правильные инструменты, тексты — живые и без Markdown.
- Подправь промпты в `app/agent/prompts/*.md`: `system.md`, `write_post.md`, `revise_post.md`,
  `extract_profile.md`, `reply_comment.md`, `weekly_report.md`. Плейсхолдеры `{{var}}` не
  переименовывай.
- В `.env` для учёта расходов (`/costs`) для Pro: `LLM_PRICE_INPUT_PER_1M=500`,
  `LLM_PRICE_OUTPUT_PER_1M=500` (на бесплатном пакете деньги не списываются, но цифры полезны
  для отчёта по затратам).

**Тесты (без сети и ключей):** подмени HTTP-ответы (`httpx.MockTransport` или monkeypatch SDK).
Проверь:
- конвертацию `tools` → `functions` и истории с `tool`-сообщениями;
- разбор ответа с `function_call` в `ToolCall`;
- обычный текстовый ответ;
- ошибка API → `LLMError`;
- `usage` читается из `raw`.

**Готово, если:** проверки зелёные, с `LLM_PROVIDER=gigachat` сценарий выше проходит живьём.
PR: `feat: GigaChat LLM provider with function calling`.

### Задача A2 — картинки через GigaChat (P0)

**Цель:** «пост с картинкой» приносит осмысленную картинку по теме, без текста на изображении.

**Файлы:**
- новый `app/images/gigachat_provider.py` — класс `GigaChatImageProvider(ImageProvider)`,
  `name = "gigachat"`;
- `app/images/factory.py` — ветка `if provider == "gigachat": ...`, `IMAGE_PROVIDER=gigachat`;
- новый промпт `app/agent/prompts/image.md` — «описание сцены»;
- `app/services/posts.py::create_draft` — только блок генерации картинки;
- тесты.

**Как:** у GigaChat генерация — встроенная функция `text2image`. Запрос в chat completions с
`function_call: "auto"` и текстом «Нарисуй ...». В ответе — `<img src="ID_ФАЙЛА" .../>`, файл
скачивается по ID (в SDK есть метод получения изображения). Сохрани в `self.output_dir` и верни
`Path`. Сверь формат по документации «Создание изображений».

**Описание сцены (`image.md`):** из темы поста и профиля компании — 1–2 предложения, что
нарисовать: объект, обстановка, стиль, свет. Без надписей и логотипов.

**Обработка сбоев:** сейчас ошибка генерации роняет создание черновика. Сделай так: при ошибке
картинки пост создаётся **без картинки**, а в ответе агента (результат инструмента
`create_post_draft`) — предупреждение «картинку не удалось сгенерировать».

**Не ломай:** если у компании есть свои фото, `create_draft` получает `image_path` — тогда
генерация не нужна, это уже работает. Интерфейс `ImageProvider` в `app/images/base.py` не меняй.

**Готово, если:** с `IMAGE_PROVIDER=gigachat` пост с картинкой приходит с осмысленным
изображением; при сбое генерации пост всё равно создаётся.
PR: `feat: GigaChat image generation with scene prompt`.

### Задача A3 — ChatGPT, критерий 12 ТЗ хакатона (P0)

ТЗ хакатона требует **проверить**, можно ли использовать существующий аккаунт ChatGPT, и честно
показать результат — **не подменяя его незаметно отдельным API-ботом**.

**Минимум (обязательно):** документ `docs/CHATGPT.md`. Основа — раздел про ChatGPT в
`docs/AI_OPTIONS.md`. Что в нём должно быть:
1. Что проверили и чем (свой аккаунт ChatGPT, тариф).
2. Вывод: подписка Plus/Pro ≠ API, официального способа вызывать модели «за счёт подписки» из
   своего кода нет. С сервера в РФ OpenAI API отвечает 403.
3. Что работает:
   - **свой GPT с Actions** (OpenAPI) — ChatGPT вызывает API нашего бота;
   - **Developer mode / MCP** — проверь на своём аккаунте, есть ли запись на твоём тарифе;
   - **Codex CLI** со входом через ChatGPT (`codex exec`) — только как эксперимент, серая зона
     по правилам тарифа.
4. Чего не делаем: автоматизацию браузера chatgpt.com (нарушает правила, ломается).
5. Скриншоты или шаги, как это показать на защите.

**Если останется время:** демо «Свой GPT с Actions» — владелец пишет в ChatGPT «сделай пост
про акцию», черновик приходит в Telegram на согласование. Для этого нужен небольшой HTTP API
бота с токеном доступа и публичный HTTPS-адрес. **Сначала напиши Уралу** — домен и сервер на нём.

### Задача A4 — автономные черновики, критерий 8 (P1)

**Цель:** без сообщений от пользователя бот сам предлагает тему, пишет пост и присылает
черновик на согласование.

**Файлы:** `app/scheduler/jobs.py::generate_daily_drafts`, `app/scheduler/setup.py`,
`app/config.py`, `.env.example`, новый промпт `app/agent/prompts/suggest_topic.md`, тесты.

**Что сделать:**
1. Перепиши `generate_daily_drafts`, сейчас он завязан на заглушку контент-плана. Для каждой
   компании, у которой заполнен профиль и есть ответственный:
   1. Возьми темы последних постов (`PostRepo.list_for_business`), чтобы не повторяться.
   2. Попроси LLM предложить одну тему (промпт `suggest_topic.md`, ответ — короткая строка).
   3. `posts.create_draft(..., with_image=True)`.
   4. `approval.submit_for_approval(session, post, container.notifier, <telegram_id ответственного>)` —
      см. `_owner_chat_id` в том же файле.
2. ⚠️ Работу по каждой компании оборачивай в `async with usage_scope(session, business.id):`
   (`app/services/usage.py`), иначе расходы не запишутся на компанию.
3. Ошибка одной компании не должна останавливать остальные: `try/except` + `log.exception`.
4. Расписание: по образцу отчётов (`REPORT_INTERVAL_MINUTES` в `setup.py`) добавь
   `AUTO_DRAFTS_INTERVAL_MINUTES`: `0` — каждый день в 9:00, `N` — каждые N минут (для демо).
   Включается флагом `ENABLE_AUTO_DRAFTS=true`.

**Готово, если:** с `ENABLE_AUTO_DRAFTS=true` и `AUTO_DRAFTS_INTERVAL_MINUTES=5` через 5 минут
ответственному приходит черновик с кнопками. Тест — с mock-LLM и FakeNotifier
(см. `tests/conftest.py`).

## 3. Правила (обязательно)

1. **Не менять без согласования с Уралом:** `app/*/base.py` (интерфейсы `LLMProvider`,
   `ImageProvider`, `Publisher`), `app/db/models.py`, машину состояний поста
   (`ALLOWED_TRANSITIONS` в `app/services/posts.py`), `app/services/notifier.py`.
   Если без этого никак — остановись и напиши Уралу.
2. **Публикация — только после согласования:** не давай агенту инструмент публикации и не
   переводи посты в `approved` в обход `services/approval.py`. Это сторожат тесты.
3. Тексты бота — только в `app/bot/texts.py` (новое — в конец файла, в свою секцию
   `# --- поток A ---`), клавиатуры — в `app/bot/keyboards.py`, промпты — в `app/agent/prompts/`.
4. **Секреты** — только в `.env`. Перед пушем проверь, что в diff нет `.env`, ключей и `data/`.
5. Перед каждым PR:
   ```bash
   git pull --rebase origin main
   ruff check . && ruff format --check . && pytest && python -m app.main --check
   ```
6. Тесты — без сети и ключей. Существующие тесты не удалять и не ослаблять.
7. **Деплой на сервер делает Урал** после слияния PR — сам на сервер не заходи.

## 4. Как сдавать

- Одна задача — один PR, в описании: что сделано, как проверить, что затронуто в общих файлах.
- После A1–A3 допиши раздел «Ограничения» в `docs/FEATURES.md` (черновик уже есть).
- Отметь сделанное ✅ в `docs/TASKS.md`.
- Вопросы — в issue #14 на GitHub или Уралу в личку.

**Порядок важности:** A1 → A2 → A3 обязательно к демо; A4 и A5 — сильно усиливают демо; A6 —
по возможности.
