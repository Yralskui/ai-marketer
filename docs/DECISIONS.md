# Принятые решения

Формат: решение — почему — как пересмотреть. Новые решения добавляем в конец.

1. **Корень проекта — сама папка репозитория**, без вложенной `ai-marketer/`. Так проще
   клонировать и запускать (`python -m app.main` из корня).

2. **`app/container.py` — единая сборка зависимостей.** Зависимости передаются в aiogram DI
   (`dp["container"]`) и аргументом в задачи планировщика. Без глобальных синглтонов сервисы
   легко подменять в тестах.

3. **Протокол `Notifier` вместо ссылки на бота в `AgentContext`.** Сервисы и агент не
   импортируют aiogram, а в тестах подставляется `FakeNotifier`. Реализация для бота лежит в
   `app/bot/notifier.py`.

4. **Публикатор получает `publish(post, channel)`**, а не только `post`. Так публикатор не
   ходит в БД и остаётся чистым адаптером к API соцсети. Есть необязательный
   `check_channel()` для `/status`.

5. **Двойная защита «только после согласования».** `approval.py` — единственный, кто
   переводит пост в `approved`/`scheduled`. `publishing.py` всегда вызывает
   `ensure_publishable()`. У агента нет инструмента публикации, тест это проверяет.
   `PublishNotAllowedError` не глотается, а пробрасывается: это нарушение правил, а не сбой.

6. **Правка возвращает пост в `draft`** (а запланированный — снимает с расписания), после чего
   нужно новое согласование. Клиент не должен получить в канале текст, которого не видел.

7. **Кнопка «Изменить» вызывает `posts.revise` напрямую, без полного цикла агента.** Так
   быстрее и детерминированнее. Свободный текст вида «сделай пост #3 короче» по-прежнему
   идёт через агента (`revise_post`).

8. **Подсказка `task=` в `LLMProvider.chat`** ("agent", "write_post", ...). Реальные провайдеры
   её только логируют, mock выбирает по ней шаблон. Это честнее, чем угадывать задачу по
   тексту промпта.

9. **Время в БД — naive UTC.** SQLite не хранит часовой пояс. Перевод в `TIMEZONE` и обратно —
   в `app/utils/time.py`. «Завтра в 10 утра» разбирает `dateparser` с предобработкой «утра /
   вечера / в 10», потому что сам он это понимает плохо.

10. **Один бизнес на владельца.** Пользователь из `ALLOWED_USER_IDS` при первом сообщении
    получает свой бизнес. Канал по умолчанию берётся из `TELEGRAM_CHANNEL_ID`
    (`services/accounts.py`). Для команды из двух человек это значит, что у каждого свой
    профиль и посты, а канал общий.

11. **Связь пост ↔ пункт контент-плана — только `Post.plan_item_id`.** Взаимные FK
    (`ContentPlanItem.post_id`) дали бы цикл, который SQLite и `create_all` обрабатывают плохо.
    С обратной стороны есть `ContentPlanItem.post` (relationship).

12. **Enum-ы — VARCHAR со значением** (`native_enum=False`, `values_callable`), плюс явный
    `NAMING_CONVENTION`. Так Alembic подключится без переименований.

13. **Транзакции:** сессия на одно обновление Telegram (middleware). `commit` выполняется после
    хендлера, а внутри сервисов — только перед внешним эффектом: показом черновика с кнопками
    и публикацией. Иначе кнопка могла бы ссылаться на несохранённый пост.

14. **FSM — `MemoryStorage`.** При перезапуске бота незавершённый ввод (правка, время)
    теряется. Для хакатона это приемлемо. TODO (поток B): RedisStorage.

15. **Разметка бота — HTML** (`DefaultBotProperties(parse_mode=HTML)`): весь динамический текст
    проходит через `html.escape`. В канал посты уходят с `parse_mode=None`, чтобы символы LLM
    вроде `<` или `*` не ломали отправку.

16. **Лимиты Telegram.** Для поста с картинкой LLM просят уложиться в ~1000 символов.
    Если текст всё же длиннее 1024, публикатор отправляет фото и текст двумя сообщениями.
    Жёсткая обрезка до 4096 — в `posts.clean_post_text`.

17. **Ruff:** E501 отключён — длину строк держит `ruff format`, а длинные тексты бота не
    дробим. ASYNC240 тоже отключён: `Path.exists()` на локальных картинках выполняется
    мгновенно.

18. **Dispatcher собирается один раз за процесс.** Роутеры — модульные синглтоны aiogram.
    Поэтому сквозной тест бота (`tests/test_bot_flow.py`) — один тест-сценарий.

19. **Защита от двойной публикации и повторы** (`services/publishing.py`,
    `publishers/telegram.py`).
    - «Опубликовать сейчас» работает под блокировкой поста и перечитывает статус из БД: двойной
      клик не опубликует пост дважды, а опубликованный пост не вернётся в `approved`.
    - Перед обращением к соцсети пост атомарно «захватывается» в БД
      (`PostRepo.claim_for_publish`: `publish_attempts + 1`, только если счётчик и статус не
      изменились), и захват коммитится. Это защищает и от второго процесса.
    - Автоповтор — только для ошибок, после которых Telegram точно не принял сообщение: 429
      (ждём `retry_after`, не дольше 60 с) и 5xx (до 3 повторов с паузой 2/4/8 с). Сетевой
      сбой не повторяем: сообщение могло уйти. Пост уходит в `failed` с подсказкой проверить
      канал.
    - О сбое публикации по расписанию узнают ответственный за компанию и администраторы.
